# Scheduled task prompt（雛形）と軽量運転のルール

Routine「期限と受け取りボード」に設定している prompt の雛形と、軽量運転・省トークン運転のルールです。
`{{...}}` の部分は実際の値に置き換えて Routine 側に設定してください（このリポジトリには実際の値を書かない）。

- 起動：cron `51 8,20 * * *`（Asia/Tokyo）＝毎日 8:51／20:51 JST の1日2回。迷ったら `list_triggers` で実際の設定を確認し、そちらを正とする。
- 必要なコネクタ：Gmail / Google Drive / Google Calendar / Claude_Code_Remote。完了時のプッシュ通知はオン。
- 軽量運転・省トークン運転のルールの正本はこのファイル（[`docs/update-procedure.md`](../docs/update-procedure.md) には複製しない）。書き換えたら Routine 側の prompt にも反映すること。
- 2026-10-12 時点で、Routine は Drive 上の Google ドキュメント「00_更新手順（次回の自分へ）」と「00a_省トークン運転ルール」を読んで動いている。このリポジトリはその内容を伏せ字にして写したもの。どちらかを直したら、もう一方も合わせる。

## ■ 軽量運転（毎回）

- サブエージェント（Agent tool）・並列タスクは使わない。すべて自分で直接ツールを呼ぶ。
- 読むのは台帳の「最後に読んだメールの受信時刻（JST）」より後の未処理メール全部。1回の上限は200件（目安。ユーザーから「上限を◯件にして」と言われたらこの数字と Routine の prompt の両方を書き換える）。1日2回運転のため前回から8〜16時間空き、1回の新着は多めになりやすい。
  - 未処理が200件以下なら全部読んで今回で追いつく。
  - 200件を超えたら古い順に200件だけ処理し、台帳の「最後に読んだメールの受信時刻」は実際に読んだ最後の1通の時刻にする（日単位に丸めない）。台帳に「残り◯件、続きは次回」と明記する。
- 全メールの再列挙・ID全数検証・過去分の掘り起こしはしない（調査依頼があったときだけの特別作業）。
- 各メールは要点1〜2行で記録する。取引・期限・金額に関わるものだけ `get_thread`（PLAIN_TEXT）で本文まで読み、広告・キャンペーンは件名と分類だけで済ませる。
- 新着が0件なら、ボード・カレンダー・メールDBには何もせず、台帳の「最後に確認した日時」だけ進めて終了する。
- 不明点があっても質問で止まらず、手順書と台帳の前例に従って判断し、最後まで終わらせる（実行中のセッションを見ている人はいない）。

## ■ 省トークン運転（2026-10-10 新設）

いちばん重いのは「ボード（Artifact）の全文読み込み＋publish」と「台帳・メールDBの丸ごと書き直し」。そこでボードの更新を毎回やめ、台帳を短くする。ボードの更新頻度と台帳の書き方については、この節が `docs/update-procedure.md` より優先する。

### 1. ボードを更新するのは次のときだけ

通常の回はボードを開かない（`action:"read"` も publish もしない）。

- (a) **週次更新**：毎週土曜 20:51 の回。前回のボード更新以降にたまった内容をまとめて反映し、日付が進んだときの直し（`TODAY`、今日やること、`ce-soon`→`ce-past` など）もこの回にまとめて行う。
- (b) **緊急時**：次のどれかに当たる「新しい種類」の出来事があった回だけ。
  - マイナポータル等の行政手続きの新規事案
  - 金融機関（銀行・証券・カード）での新しい種類の操作（新規口座開設、資金移動の新規発生や大幅な増額、認証設定の変更など）
  - カレンダー登録した期限が48時間以内に迫っているのに、ボードに載っていないもの

  同じ事案の繰り返し（同じ証券会社のログイン通知の25回目、26回目…など）は緊急扱いにしない。台帳の追記と PushNotification だけで済ませる。
- (c) ユーザーが明示的にボード更新を指示したとき。

### 2. 通常の回（ボードを開かない回）

1. 手順書と台帳を読み、前回の続きから新着を取得して分類する。
2. メールDBに追記する（広告・案内は下の短縮形）。
3. Google カレンダーへの登録・更新は従来どおり。`create_event` を呼んだら .ics を作り直して SendUserFile する。
4. 台帳を更新する。
   - 「ボード最終更新」（日時）と「ボード未反映の新着」（まだボードに載せていない主要項目を1項目1行）の2項目を置く。通常の回は、今回の主要項目（重要・取引・期限・セキュリティ・到着）を「未反映」に1行ずつ追記する。広告・案内は書かない。
   - バッチログは今回分を5行以内にし、前回分を1つだけ残してそれより古いものは消す（詳細はメールDBに残っている）。
   - 「セキュリティ・要対応事項」「残っている宿題」は、変更があった項目だけ書き換える（内容は省略せず全体を引き継ぐ）。
5. 緊急の事案に気づいたら、全件処理を待たずに PushNotification で速報する。

### 3. 週次更新・緊急更新の回

- ボードの更新手順は `docs/update-procedure.md` の「■ Artifact（ボード）を編集するときの実務」のとおり。反映するのは台帳の「ボード未反映の新着」の全項目と今回の新着。必要ならメールDBの該当日を読む（広告は読まなくてよい）。
- 更新したら台帳の「ボード最終更新」を今回の日時にし、「ボード未反映の新着」を空にする。
- ボード末尾の変更履歴は1回分を5行以内にまとめる。

### 4. メールDBの短縮形

- 広告・キャンペーン・求人・不動産・案内は本文を読まず件名だけで分類し、1ブロックを「日時 | 差出人 | 件名」＋「ID / 分類: 広告」の2行で書く（「なし」の項目は並べない）。
- 取引・期限・金額・セキュリティに関わるものは従来どおりの詳しい形式。

### 5. このルールの変更

頻度（週1→月1など）を変えるときは 1.(a) を書き換え、Routine の prompt も合わせる。毎回更新に戻す場合も、この節と prompt の両方を書き換える。

## prompt 本体

```text
自分宛ての繰り返しタスクです。判断に迷っても質問で止まらず、最善の判断で最後まで実行してください（このセッションを見ている人はいません）。

## 最初にすること

1. Google Drive のフォルダ {{MANUAL_FOLDER_ID}} 内の「00_更新手順（次回の自分へ）」と「00a_省トークン運転ルール」をタイトルで検索して読む（ファイルIDは作り直しで変わるので、IDではなくタイトルで探す）。これが唯一の正しい手順書で、この prompt と食い違う場合は手順書を優先する。ボードの更新頻度と台帳の書き方は 00a が 00 より優先する。
2. 今月分の「01_記録台帳 YYYY-MM」（フォルダ {{LEDGER_FOLDER_ID}} の直下。タイトル検索）を読み、最後に読んだメールの受信時刻・ボード最終更新・ボード未反映の新着を確認する。必要なら「メールDB YYYY-MM-DD」の該当日も読む。
3. 対象のボード（Artifact）：{{ARTIFACT_URL}}（このURLを上書き更新し、新しい Artifact は作らない）。更新するのは 00a の条件（毎週土曜20:51・緊急時・ユーザー指示）に当たる回だけ。更新する回は publish 前に action:"read" で最新版を取得し、返ってきたファイルを最初から最後まで読み切ってから編集する。

## やること

1. Gmail（{{GMAIL_ACCOUNT}}）で、台帳の「最後に読んだメールの受信時刻」より後の新着だけを取得する（1回あたり上限200件の目安）。
2. 手順書の分類・色分け・重要イベントの扱い・カレンダー書き込みルールに厳密に従って処理する。Google カレンダーの colorId と件名は create_event／update_event のたびに手順書の表と照合し、前回登録分を真似しない（航空券・新幹線を買った日は買い物=7、乗る日だけ移動=9）。
3. 処理結果を反映する：Google Calendar／「01_記録台帳 YYYY-MM」（trash→create）／「メールDB YYYY-MM-DD」（trash→create）／ボード（00a の条件に当たる回だけ）。create_event を1件でも呼んだら、今後の全イベントで .ics を作り直して SendUserFile で渡す。緊急の事案は気づいた時点で PushNotification。
4. 新着が0件なら、台帳の確認時刻だけ進めて終了する。

## 注意

- サブエージェント／並列タスクは使わず、すべて自分で直接ツールを呼ぶ。
- 手順書に矛盾や足りない点を見つけたら、その場で手順書も直す（一回限りで終わらせず標準ルールとして書き足す）。trash→create で作り直すときは、作成後に全文が一致することを確認してから旧版を trash する。
- 完了条件：新着がすべて処理され、カレンダー・台帳・メールDB（ボードを更新した回はボードも）の内容が一致し、台帳の「未処理の新着」が0件。
```
